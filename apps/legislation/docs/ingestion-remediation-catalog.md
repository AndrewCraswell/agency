# Ingestion remediation catalog

This document explains production problems found while moving legislation
ingestion onto Trigger.dev. It is written for a reader who was not present
during the migration. Each entry answers four questions:

1. What did we observe?
2. Why did it happen?
3. What did we change?
4. How did we verify the change, and what remains unresolved?

It is a living document. Add an entry when a new failure requires code,
configuration, schema, or a controlled database repair. Update the existing
entry when later evidence changes the diagnosis or solution.

Last operational refresh: 2026-08-21 05:47 UTC. Point-in-time counts in this
catalog are verification evidence, not permanent expected values.

Transient upstream failures that are handled correctly by the existing retry
policy do not need individual entries. A failure belongs here when it exposes a
new source contract, correctness problem, orchestration defect, unsafe resource
limit, or terminal cohort that requires an operator decision.

## Start here: how ingestion works

The system has four main stages:

1. **Source synchronization** downloads legislative metadata from Congress.gov,
   GovInfo, OpenStates archives, or a state publisher.
2. **Normalization** converts each provider's format into the application's
   canonical bills, people, organizations, events, votes, and materials.
3. **Document processing** downloads linked bill text and supporting files,
   extracts usable text, and stores immutable source and normalized artifacts.
4. **Derived processing** builds document sections, validation reports, and,
   only when separately approved, embeddings.

Trigger.dev runs the background work. A **controller** divides a large job into
bounded pieces. A **worker** processes one piece. Controllers and workers call
shared ingestion functions; they do not contain separate copies of the
normalization or download logic.

PostgreSQL remains the durable source of truth. It stores checkpoints, job
history, row processing state, and short-lived leases that prevent two workers
from changing the same scope simultaneously.

## Terms used in this document

- **Checkpoint:** The last durable position successfully processed in a source
  stream. A retry resumes from this position.
- **Controller:** A Trigger task that schedules and waits for smaller worker
  runs.
- **Worker:** A Trigger task that performs one bounded unit of work.
- **Lease:** A database record that temporarily grants one worker ownership of
  a synchronization scope or publisher download slot.
- **Scope:** The exact unit protected by a lease, such as Vermont document
  partition 2 of 4 or Congress 118 amendments.
- **Resolver:** Code that converts an obsolete provider URL into a verified
  current download URL at request time.
- **Remediation cohort:** A precisely selected group of existing database rows
  that can safely be retried after a fix. A cohort is deliberately narrower
  than “retry every failure.”
- **Canonical identity:** The stable database identity for a bill, document, or
  provider record. Repairs must not create a second identity for the same
  source record.
- **Partial run:** A worker completed normally, but one or more records were
  deferred, unsupported, or failed individually. It is different from a task
  crash.
- **Version-pinned run:** A run that continues using the Trigger deployment it
  started with, even after newer code is deployed.

## How a document repair is performed

Suppose an archive contains an old publisher URL that no longer works:

1. We capture representative stored URLs and their exact errors.
2. We prove a replacement using the publisher's current official site. We do
   not guess from a similar-looking hostname.
3. We add a strict resolver that recognizes only the proven URL pattern.
4. The resolver changes the network destination only. The stored `source_url`,
   document ID, bill ID, and provenance remain unchanged.
5. We add a remediation cohort that selects only rows with the evidenced URL,
   status, and error combination.
6. We deploy the shared Trigger project, stop any older version-pinned worker
   for that state, and wait until its lease has expired.
7. We recover only the exact interrupted claims, prepare the cohort, and start
   disjoint repair partitions.
8. We verify the initial batches, the 30-minute canary, and subsequent hourly
   progress. We specifically check for the original error returning, overlap,
   task crashes, and database pressure.

Because canonical identity and stored provenance are preserved, a later full
archive import finds and updates the same document. It does not create a second
record merely because the network download URL changed.

## Deployment and run-version semantics

Trigger.dev deployment versions are project-wide immutable snapshots. A deploy
bundles every detected task and the shared ingestion functions imported by
those tasks. They are not versions of individual task types.

New runs use the current deployment. Existing runs, including child runs
created by an older controller, stay pinned to the controller's deployment.
Operational reports therefore include the Trigger deployment version so an
operator can distinguish a repaired run from a version-locked predecessor. A
shared resolver or normalizer is changed once in source, but an old run does
not hot-swap to the new implementation.

## Information required for a new entry

Every new entry must include:

1. The observed symptom and affected scope.
2. Evidence for the root cause. Do not infer a replacement URL from naming
   alone.
3. The exact code or operational repair.
4. Identity behavior: whether `source_url`, canonical IDs, checkpoints, and
   blob identities are preserved.
5. The bounded remediation predicate, when existing rows must be retried.
6. Verification evidence and the deployment/run boundary used for the canary.
7. Residual limitations or follow-up work.

Resolvers change only the fetch target. They preserve the stored provider
`source_url`, document ID, bill ID, and source provenance. A future archive
re-import therefore upserts the same canonical document rather than creating a
second source record.

## Operator workflow for a new remediation

1. Stop only the affected controller or partition when continued work can
   corrupt state or consume attempts. Do not stop unrelated lanes.
2. Capture representative stored URLs, exact errors, status, attempt counts,
   sessions, and timestamps.
3. Prove the official replacement with bounded live requests. For a URL
   rewrite, compare response bytes or validate the exact official artifact.
4. Implement a strict fetch-time resolver or host-scoped transport repair.
   Never disable TLS verification and never rewrite stored source identity.
5. Add an exact `documents:prepare-remediation` cohort. It must exclude
   `processing` rows and use `FOR UPDATE SKIP LOCKED`.
6. Deploy the complete Trigger project snapshot. Record the deployment version
   because existing controllers stay version-pinned.
7. Confirm the old worker is terminal and its ingestion lock expired. Recover
   only the exact interrupted claims using jurisdiction, shard/partition, and
   timestamp evidence.
8. Prepare the bounded cohort and launch disjoint repair partitions with a new
   rebuild ID and idempotency keys.
9. Verify initial, 30-minute, and hourly outcomes: processed count, exact error
   recurrence, leases, overlap, OOM, database sessions, and queue pressure.
10. Update this catalog with the observed result and any residual limitation.
