# Legislation diffing

`@repo/legislation-diffing/comparison` exports a pure, synchronous, browser-compatible literal text comparison. It
imports no application, core, database, network, React or Node-only modules. The package exports TypeScript source.
Sequence alignment uses [jsdiff](https://github.com/kpdecker/jsdiff), not a quadratic LCS matrix.

```ts
import { compareDocuments } from "@repo/legislation-diffing/comparison"

const comparison = compareDocuments({
  left: { id: "earlier", contentHash: "source-fingerprint-a", text: earlierStoredText },
  right: { id: "later", contentHash: "source-fingerprint-b", text: laterStoredText },
  granularity: "word"
})
```

## Contract

- `ComparisonDocument` is `{ id: string; contentHash: string; text: string }`. Pass the **complete stored text**,
  including preamble. `contentHash` is an opaque, caller-supplied source fingerprint, copied unchanged. It is not
  computed, validated as a digest, used for equality or claimed to hash normalized text.
- `DiffGranularity` is `"paragraph" | "word"` and defaults to `"paragraph"`.
- `DocumentComparison` contains `granularity`, `left` and `right` source metadata (`id`, `contentHash`, UTF-16
  `textLength`), `counts`, ordered `hunks`, and `unifiedDiff`.
- `unifiedDiff` is a standard line-based unified patch generated by jsdiff from the same full inputs, with three lines
  of context. The neutral `a/document.txt` and `b/document.txt` headers are presentation names, not source identities.
  Document identity remains in `left` and `right`. A library renderer can consume this patch without custom alignment.
- `DiffClassification` is `"added" | "changed" | "removed" | "unchanged"`. Counts are **hunk counts**, not provision,
  word or character counts. These are textual classifications, never legal classifications.
- Each `DiffHunk` contains a zero-based presentation `ordinal`, `classification`, `leftText`, `rightText`, `leftStart`,
  `leftEnd`, `rightStart`, `rightEnd` and `operations`. Ordinals are not provision identities.
- Each `DiffOperation` contains `classification: "equal" | "delete" | "insert"`, `text` and the same four ranges. Empty
  documents produce no hunks. Operations always contain nonempty text.

All offsets are absolute, zero-based, half-open **UTF-16 code-unit** ranges into the **unmodified input strings**,
matching JavaScript `slice(start, end)`. An absent side has `null` text and ranges, not a fabricated zero-width
location. Equal operations have both ranges, deletes only left ranges and inserts only right ranges. Filtering out
inserts and concatenating operation text reconstructs the exact left input; filtering out deletes reconstructs the exact
right input. Within each side the ranges partition the entire input without gaps or overlaps.

## Alignment and grouping

1. Split each whole text into literal paragraph blocks. Blank lines separate blocks; their whitespace and line endings
   stay with the preceding block. Leading blank lines form their own block. A Unicode paragraph separator (`U+2029`)
   also ends a block. Single LF, CRLF, CR or Unicode line separators remain inside wrapped paragraphs.
2. Align the complete block sequences using exact string equality. Never key, deduplicate or match by a heading, section
   number, chapter reference or position. Duplicate occurrences remain distinct.
3. Emit one hunk per unchanged block and per purely added or removed block. In paragraph mode, pair a replacement only
   when its run contains one removed and one added block. Longer unmatched runs retain separate removed/added blocks
   rather than guessing correspondence or building one oversized replacement hunk.
4. In paragraph mode a changed hunk contains a deletion and an insertion. In word mode refine each changed region using
   jsdiff over literal word, whitespace and punctuation tokens. Letter/number/combining-mark/underscore runs form words;
   whitespace runs and remaining Unicode code points are separate tokens. No locale-dependent segmenter, whitespace
   ignoring, Unicode normalization or case folding is used.

All whitespace, punctuation, duplicate text, CRLF sequences and Unicode are retained. An astral character occupies two
UTF-16 units; token boundaries are not a guarantee of grapheme boundaries. Moves may appear as deletion plus insertion.
Repeated content can have several equally valid edit scripts; jsdiff's deterministic sequence tie-breaking chooses one.
Nothing identifies which legal provision moved or whether its meaning changed.

NER, LLMs, amendment application, legal-effect interpretation, legal ASTs and USLM conversion are outside this package.

## Finite resource limits

`limits?: Partial<ComparisonLimits>` can **lower** the following exported, frozen `DEFAULT_COMPARISON_LIMITS`. Omitted
fields use their defaults. Every limit must be a finite nonnegative integer no greater than its default ceiling. Invalid
configuration throws `DocumentDiffError` with `code: "invalid_input"`.

| Limit                   | Default ceiling | Scope                                                                     |
| ----------------------- | --------------: | ------------------------------------------------------------------------- |
| `maxDocumentCharacters` |       2,000,000 | UTF-16 units per input document, checked before tokenization              |
| `maxBlocks`             |          20,000 | Combined blocks across both input documents                               |
| `maxTokens`             |         200,000 | Combined word-refinement tokens across every changed region on both sides |
| `maxEditDistance`       |           4,096 | Inserted plus deleted tokens in each block or word alignment              |
| `timeoutMs`             |           2,000 | One overall deadline for tokenization, alignment and result construction  |

Block and word counts are checked incrementally before storing the next token. Unchanged regions and wholly one-sided
regions are not word-tokenized. Entirely empty/one-sided comparisons need no alignment search.

Each jsdiff call receives its built-in `maxEditLength` limit and the remaining time until the shared deadline.
Tokenization and result construction also check that deadline; word refinements do not restart it. Checks are
cooperative, not a hard real-time interruption. Successful results are deterministic, but whether a timeout is reached
depends on runtime performance. There is no custom edit-frontier or work-accounting implementation.

Crossing any effective processing limit throws `DocumentDiffError` with `code: "resource_limit"`. There is no
truncation, approximate result, silent downgrade from word mode or success-shaped fallback. Callers should present an
explicit comparison failure rather than misrepresenting missing text as a successful comparison.

## Verification

Co-located unit tests check exact reconstruction and contiguous offsets, duplicate chapter references, movement,
paragraph splits/merges, headingless text, whitespace and Unicode, determinism, empty/identical inputs and limits. From
the workspace root, use `pnpm --filter @repo/legislation-diffing test`, `check:types`, `lint` or `test:coverage`.
